# R2 自审、人审与证据矩阵

与 [计划](R2-PLAN.md) 配合使用。每项状态为 pass / fail / blocked / not-run，并附证据路径、环境、源码指纹和适用 stage。历史 R1 测试数不算 R2 结果。

默认画面覆盖 1680/1280/780/390、1279/1280 临界点、短屏、200% 文字、中英文长内容、长对话与多条历史终态。无需机械录制全部笛卡尔积；矩阵要明确每例在哪些尺寸复验，关键交互至少桌面和手机宽度各一次。

真机软键盘/IME、其他浏览器、真实 QQ 完成链、真实供应商执行若没有测试条件，标明 not-run；模拟不等于真机。性能记录浏览器、设备/限速、视口、活跃实例数、采样时长和掉帧/长任务情况；没有测量不能宣称稳定 60fps。长对话不得让历史终态持续占用循环。

## 每次可审包

1. **可操作预览**：地址、启动/恢复办法、当前 stage、源码指纹；账户来自隔离交接，说明是否真实 API。
2. **同数据对照**：R1 baseline 与当前相同内容和尺寸，静态画面不能因动效破坏 R1 材质。
3. **原速视频**：输入设备、视口、状态来源、事件顺序可查；另给开始/中间/结束与故障关键帧。慢放不能代替原速。
4. **实际自审**：逐项写观察位置/视频时间点、问题、原因、修复、复验，不只打分。六项沿用总方案：层级、排版、材质、状态辨识、运动因果、整体一致性。
5. **反馈闭环**：每条人审意见记录原话、决定、实现、证据及是否仍待复审。不能擅自关闭用户否决项。
6. **技术范围**：pass/fail/blocked/not-run，已知缺口及影响；不使用“全部通过”掩盖未测项。

## 人审问题与放行

R2.1：会话落座能感知但不晃吗？Rail 轨迹能说明当前位置吗？浮层是否轻、稳、不拖慢操作？

R2.2：不读长文本能否分清六态？小尺寸清楚、大尺寸有层次吗？快速切换是否连贯？长时间运行会不会抢正文注意力？

R2.3：输入就绪与按钮意图明确吗？是否出现多个地方同时抢眼？整条操作链自然吗？R1 已接受的页面是否仍然成立？

实施者给出判断与证据，再由用户体验。B/C 的“可以继续”只放行下一子阶段。最终只有用户明确接受 R2，且阻断缺陷已关闭，才能写 `R2 已接受`。用户只认可部分时保持 `待人审` 或 `人审返修`。最终交接列明已接受交互合同、遗留限制、R3 所需接口以及仍未实现的飞线/银丝/Mercury。
