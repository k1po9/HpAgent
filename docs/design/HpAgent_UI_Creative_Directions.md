# HpAgent UI Creative Directions

> P1 · 创意发散与产品交互范式探索 · 2026-10-11  
> 产品定位：智能云 AI 管家。本文用于选择、修改和组合方向，不是最终信息架构、页面规格或实施计划。

## 0. 阅读方式与设计立场

这次探索的核心问题是：**当 AI 能持续承担工作时，产品能否围绕“委托如何被履行”组织体验，而不再要求用户通过聊天记录寻找一切？**

Chat 应保留为表达复杂意图、解释和澄清的语言通道，但不必成为任务、资源和成果的唯一容器。管家感应来自可靠的交接、适时呈现和持续负责，而不是拟人头像、频繁问候或未经授权的主动行动。

本文先提取 P0 的能力与约束，再提出六个互不等价的交互范式，最后比较并推荐三个融合方向。文中的构图表达对象关系和交互重心，不规定左右栏、路由、组件或屏幕尺寸。所有场景均为设计推演，不是已运行验收的演示。

## 1. 从真实能力出发：必须满足的设计输入

### 1.1 可以重新组织的产品能力

| 能力 | 用户真正需要完成的事 | 对新设计的启示 | P0 依据 |
| --- | --- | --- | --- |
| 有限请求与多轮对话 | 临时问一个问题，继续讨论，核对一次执行 | 对话可成为局部交流层，不必霸占全局中心 | C01–C08 |
| 持续委托 | 交代目标、约束、预算和完成条件，离开后仍有人负责 | Work 可以成为独立的生活事务或责任单位 | W01–W07、W10 |
| 定时与提醒 | 指定时刻或每天做一轮工作 | 时间可以成为导航轴；调度时间不能冒充完成期限 | W04 |
| 研究与通用工作 | 使用资料、形成可追溯结果、检查证据 | 可按工作类型呈现不同观察与审阅界面 | W03、F08、H04 |
| 长期资料与权限 | 保存、查找、授权、撤回、核对版本和来源 | 资料可以作为发起工作的入口；保存和使用需分别成立 | F01–F07、W09 |
| HTML 成果及版本 | 从完成回答生成成果、修改、预览、下载 | 成果可成为下一轮协作的中心对象 | H01–H04 |
| 审批、投递与验收 | 处理需要人决定的事，确认交付事实 | 人机责任交接比全量活动流水更有用户价值 | C08、W11–W12 |
| 账户与 QQ 连续性 | 在验证过的入口继续使用同一账户 | 可以有跨入口管家体验，但不能隐含合并历史或随意指定收件人 | A01–A04 |

研究 evidence、Run 冻结范围搜索、Artifact 作为 Work input/evidence，以及更完整的 Requirement/时区表达，都属于已有后端的接入空间，不应误判为需要新建整套能力。

### 1.2 任何创意都不能改写的业务语义

| 事实与约束 | 必须怎样表达 | 不能怎样表达 |
| --- | --- | --- |
| Conversation、Work、Run 各有身份 | 分清交流、持续委托、一次执行；一个 Work 可以多次运行 | 将 Work 塞成一条助手消息，或用取消 Run 表示停止委托 |
| 同一 Conversation 只有一个活跃 chat Run | 执行时可写本地草稿，明确尚未提交；其他对话可独立工作 | 暗示正在执行的请求可被随时追加、编辑或分叉 |
| 接受、执行、终态不同 | 提交中、结果未知、已接受、执行中分别呈现 | 发送按钮按下即显示“管家已办妥” |
| Work 是多轴状态 | 同时回答：委托是否仍有效、本轮怎样、在等什么、成果到哪一步 | 用一个完成百分比压平生命周期、继续条件和交付 |
| 资源主体和操作独立授权 | 显示授予哪个 Conversation/Work、哪些操作、是否递归 | 以拖入空间、关联对话、保存文件替代授权 |
| Run 输入冻结，首次选择固定版本 | 区分候选、已选版本和实际读取；新增通常下轮生效 | 文件靠近 Agent 就显示已被读取，或补资料后当前 Run 自动扩容 |
| 撤权检查当前后续访问 | 显示撤权确认和受影响运行；清理敏感观察缓存 | 承诺抹掉已发生的读取，或一律立即终止全部运行 |
| 版本不可偷换 | 原 Work 交付始终指向精确版本；新版独立存在 | 自动用最新手改版替换原交付证据或原验收对象 |
| 成功有不同证据 | 生成、发布文件、长期保存、渠道接受、成果验收各自核对 | 把预览打开、下载成功或普通文字回答等同 Work 完成 |
| 部分成功与未知责任必须保留 | 保存成功而授权失败只补授权；未知提交复用原意图核对 | 重发整个流程；把网络断开、加载失败都显示为任务失败 |
| 持续预算累计 | 同时解释使用、预留、上限；明确增额的对象与效果 | 修订、重试、分支执行后清零，或增额自动解除权限/账户日额度 |
| 暂停与停止需要收敛 | pausing/stopping 期间仍展示未决操作与投递责任 | 用户关页面、暂停动画或按停止后立即显示全部结束 |
| 状态更新机制不统一 | 显示必要的新鲜度；事件缺口回查权威 snapshot | 声称所有文件、成果、通知均全局即时同步 |
| 身份和安全呈现 | 账户隔离、过期清理；诊断安全投影；HTML 受限预览 | 让生成 HTML 获得产品控制权，或向模型自动塞入账户全部资料 |

契约依据：Interaction §1–8。设计可以减少技术术语，但不能删掉帮助用户作决定的事实。

### 1.3 必须留在愿景层或验证层的能力

**[扩]** 多人共享 ACL、跨设备草稿、服务端通知已读、对话编辑/分叉/删除归档、成果公共托管、任意收件人、weekly/cron、用户任意创建 Agent 团队、通用未知 operation 人工解除、原子跨对象操作、严格客户端 Artifact parent CAS，目前均不能当成现成能力。

**[待核]** 实际部署工具/文件开关、研究网络来源、模型理解质量、QQ 真实投递、长跑恢复和文档 worker。文件支持受类型白名单约束，不假设图片/音视频输入、PDF 转换或 Office/PDF 内嵌预览已开放。

特别影响创意的差异：G02 不保证草稿/命令跨刷新恢复；G03 Artifact 修改存在跨客户端基准竞争；G04 研究成果手工修改规则需核实；G05 输入列表含撤销历史，要消费 available；G06 输出撤权不承诺全部运行立即停止；G07 审批触发覆盖未知；G08 不宣称所有 HTML 下载都有相同 CSP；G10 补资料不保证自动解除 awaiting_input。

## 2. 六种方向：先比较它们以什么为中心

| 方向 | 第一组织原则 | 用户的核心动作 | AI 如何“出现” | Chat 的地位 |
| --- | --- | --- | --- | --- |
| A 责任交接台 | 下一件需要谁承担的事 | 交代、接回、决定、验收 | 负责交接的管家 | 交代与解释通道 |
| B 事务空间 | 用户正在处理的生活/工作情境 | 进入一个情境，携带对象工作 | 随情境出现的助手 | 情境内的交流记录 |
| C 工作剧场 | 一次工作的真实执行变化 | 观察、定位阻塞、介入 | 可观察的执行现场 | 发起与阶段说明 |
| D 成果生长台 | 最终想得到并继续使用的东西 | 从成果反向交代、比较、再加工 | 成果旁的制作能力 | 修改意图与来源 |
| E 时间管家 | 持续委托的节律与下一次接触 | 安排、离开、回来接收 | 在正确时刻承担责任 | 安排和临时商量 |
| F 资料关系桌 | 资料、使用关系与成果血缘 | 选材料、连到用途、追来源 | 在授权关系中工作的能力 | 对选定材料提问 |

区别在于操作语法和寻找信息的路径，不在配色。A 让用户决定“下一步谁来”，B 让用户进入“这件事的情境”，C 让用户看“正在发生什么”，D 让用户改“我要拿到的东西”，E 让用户安排“何时再见”，F 让用户判断“这些东西怎样关联”。

## 3. 方向 A：责任交接台——只在需要你时把事情交回来

### 核心创意与第一幕

设计哲学：管家替用户持有责任，界面优先呈现需要用户参与的交接，而不是要求用户巡视全部任务。完成不是卡片消失，而是责任已有清晰去向。

再次打开产品，第一幕是一个简短交接：“已有研究成果可核对；一项委托需要你决定预算；其余委托按当前计划等待或执行。”这些陈述由已读取状态按规则生成 **[前]**，并可展开依据；数据尚未加载完整时不报精确总数。首次使用则只出现“交代一件事”，配一个说明如何交接的小例子，不假造待办。

```text
交代一件事 → 委托被接受 → 管家承担
                              │
              需要你的决定 ←──┤──→ 原成果交给你
                    │                    │
                    └─ 明确决定后回查 ────┘
                 随时查看全部委托与责任记录
```

### 对象组织与发起方式

任务按“当前责任和可行动性”聚合，但完整 Work 生命周期仍可查。对话作为每次交代、解释和澄清的记录挂在相关对象上；长期资源通过本次委托的使用清单进入；成果作为可核对的交付包出现，含版本、来源、保存和交付事实。

用户写“帮我研究三种家庭宽带方案”，再选择一次完成或持续委托。基础路径用可编辑的委托摘要确认目标、资源、预算及成果要求 **[前]/W01**；自然语言直接委托可走 **[现]/W02**，但不是一个保证只起草、不执行的专用解析接口。若要“任何自然语言都先结构化预演、确认后才执行”的统一保证，需要受约束的意图解析契约 **[扩]**。

### 执行变化与成果复用

运行正常时界面保持安静，仅在状态确有变化时更新短句。需要审批、预算决定、补资料、验收或核对投递时，展开对应交接内容，而非统一显示“请确认”。不把 unknown operation 包装为可以点击解除的待办；显示真实阻塞和目前可用的核对路径。

用户打开交付包即可查原成果、证据和长期入口，分别决定下载、保存、验收或作为另一 Work 的 input/evidence。复用不继承旧授权，也不把“我看过了”记成服务端已读。

### 视觉、动效与空间

采用短笺、交接签和清晰的事实印记，留白表达低打扰。动效只服务责任转移：后端确认后，一张交代签收束成稳定的委托锚点；未决事项保留未闭合的边框及文字原因。避免红点瀑布和“管家忙碌中”的持续表演。键盘可逐条处理，但始终能跳过并查看全局。

### 完整交互故事

1. 林女士交代比较宽带套餐，选择研究工作，限定来源和预算，显式授权已有需求说明。
2. 提交后先显示“正在确认是否接受”；收到 Work 后才显示已接受，后续再确认运行。
3. 她离开。再次进入时，交接台显示这项工作的真实继续条件。若因预算阻塞，列出已用、预留和增加上限的影响。
4. 她提高明确额度；界面核对结果，再按后端条件观察恢复，不宣称增额必定立即启动。
5. 报告完成后，她打开原版本查看研究证据。若界面预览失败，仍可读取报告或下载，交付包不被改成“生成失败”。
6. 她完成符合条件的原版验收，另存报告，并将精确成果引用到下一项比较工作；新工作另行确认资源范围。

### 亮点、风险与可行性

| 项目 | 判断 |
| --- | --- |
| 独特价值 | 把 AI 产品的主循环改成责任交接，减少“我是不是还得盯着它”的负担 |
| 使用风险 | 自动排序可能藏起重要委托；频繁要求决定会退化为审批后台；措辞可能夸大自主性 |
| 基础可行性 | **[现]** W01–W12、C08、F01/F06、H04；**[前]** 按 continuation/reason 聚合、展开差异化交接、串联原版成果；各查询部分失败分别展示 |
| 愿景扩展 | **[扩]** 跨设备注意事项已处理状态、基于个人偏好的可靠优先级、主动提出新委托；后者只能建议，执行仍需授权 |
| 待核与恢复 | G02/G10；补资料后重新读取继续条件；提交未知保留原意图；预算/审批/投递风险采用各自决定流程 |
| 适用边界 | 最适合同时委托多件事、主要关注结果的普通用户；不适合把详细执行研究放在第一层 |

## 4. 方向 B：事务空间——产品随“我正在处理哪件事”组织

### 核心创意与第一幕

设计哲学：人往往记得“搬家这件事”，而不记得它属于哪个对话、文件目录或任务模块。把一段生活或工作情境作为进入产品的入口，在其中聚合相关对象。

第一幕是几个命名清楚的情境入口，例如“搬家准备”“家庭采购”“学习计划”，每个只显示当前锚点和最近已确认变化。基础版中这些空间是用户组织的本地视图 **[前]**，不是已有服务端项目实体；不能承诺跨设备持久存在。空账户可以先完成一项工作，再由用户决定是否整理成空间，避免先搭框架。

```text
搬家准备（情境视图，不是权限容器）
  ├─ 决定：选择搬家公司 → 比较成果
  ├─ 委托：研究报价 → 本轮运行 / 交流
  ├─ 资料：物品清单 → 指定版本 / 使用权限
  └─ 安排：搬家前提醒 → 时间 / 收件事实
进入“决定”时呈现比较；进入“资料”时呈现来源与使用
```

### 对象组织与发起方式

Work 是情境中的委托，Conversation 是商量过程，长期资源是可引用对象，成果是可以继续使用的情境资产。一个文件可以出现在多个情境视图中，而不移动原入口或复制字节。既有 Work–Conversation 关系和成果血缘使用真实关系；自定义跨对象集合仅是本地编排。

用户进入“搬家准备”，选清单后说“基于这份清单研究三家方案”。空间预填目标和候选资料，用户核对具体 Work 授权。进入空间、拖入文件或将 Conversation 关联 Work，都不会自动把历史和权限导入。

### 执行变化与成果复用

情境保持稳定，焦点内的工作界面按对象类型变化：研究时出现证据与报告；提醒时出现下次时间与投递；HTML 制作时出现版本预览；临时问答仍可展开消息。采用已知对象类型和状态驱动的有限呈现 **[前]**，用户可固定当前视图，运行事件不抢走焦点。

成果可留作该情境的入口，也可引用到其他情境。跨情境带过去的是对象引用和可追溯来源；创建新 Work 后，另行选择 input/evidence 或资源 grant，不产生隐藏的“空间共享授权”。

### 视觉、动效与空间

使用“进入—聚焦—返回”的连续缩放感，让同一对象在空间概览和局部工作中保持形状与名称。空间用小幅色彩、材质和标题区别，不画需要用户理解的 3D 房屋。移动端按情境逐级展开；缩放动画可以关闭，并提供固定的返回路径与最近对象。

### 完整交互故事

1. 周先生建立本地“搬家准备”视图，将已有清单入口和相关对话放入其中；提示这只是当前设备的组织方式。
2. 他从清单发起研究 Work，明确授权该 Work 读取，另设输出保存要求与必要权限。
3. 接受后进入研究呈现，看到实际来源和执行状态；清单仍可独立管理。
4. 他上传补充清单。界面显示文件保存与授权分别成功，并解释新增资料通常供下一次运行使用；不承诺当前研究已读到。
5. 如需改变本轮目标，他通过符合资格的 Work 修订表达新要求；保留旧要求和运行记录，核对新继续条件。
6. 原成果到达后，他在同一情境内比较方案，验收精确版本，再建立搬家前的一次提醒。
7. 两周后从该情境返回，可找到原报告和资料来源；换设备时基础版仍可按真实 Work/文件查询，不能假装本地空间已同步。

### 亮点、风险与可行性

| 项目 | 判断 |
| --- | --- |
| 独特价值 | 把功能模块转成一个生活情境中的不同工具，减轻用户在任务、文件、对话间搬运上下文的负担 |
| 使用风险 | 空间过多会变成新文件夹迷宫；可能误认为同空间资料都已授权；动态视图导致位置记忆失效 |
| 基础可行性 | **[现]** C01、W05/W08/W09、F02–F06、H04；**[前]** 本地集合、按对象关系聚合、情境预填、类型驱动展示；明确加载范围与同步边界 |
| 愿景扩展 | **[扩]** 服务端情境实体、跨设备空间组织、空间级长期记忆与可编辑偏好；共享空间还需要成员权限体系 |
| 待核与恢复 | G02/G05/G10；对象丢失或权限变化显示不可用引用；本地空间失效不影响真实 Work 和文件；不自动重建已删除目录 |
| 适用边界 | 最适合跨多周、涉及多种资料和委托的事务；只有一次提问时不强制建空间 |

## 5. 方向 C：工作剧场——让真实工作过程成为界面

### 核心创意与第一幕

设计哲学：用户不必阅读工具日志才能理解 AI 正在做什么。把真实执行事实转译成可观察的现场，让“等待”成为能够理解、必要时能够介入的过程。

第一幕是用户最近关注的工作现场，显示“已接受的目标”“当前已知活动”“已有产物”“现在为何等待”。没有活跃工作时展示最近一次的结果与过程摘要，不制造始终在运转的动画。

```text
已确认目标 ── 本次执行现场 ── 已发布输出
                  │
       资源范围 / 实际读取 / 可见分支
                  │
          阻塞原因 → 合法介入动作
历史事件可检查；未来步骤只是计划，不是已发生事实
```

### 对象组织与发起方式

Work/Run 是主角，对话承担开场交代与解释；长期资源以本轮候选、固定版本、实际读取的不同事实出现；成果从执行现场独立出来成为稳定对象。内部 trace 和分支只按安全投影呈现，不展示虚构推理或模拟 Agent 人格。

用户选择“开始一项工作”，提交目标与资源。可选择现有 ReAct/Plan-and-Execute 策略，但计划仅是执行参考；图上的节点不能被拖成任意后端工作流。复杂任务的有界分支由真实执行产生，用户不在此自由组建 Agent 团队。

### 执行变化与成果复用

真实事件到达时，相应对象状态变化：资源进入候选范围不等于读取；已读取需有依据；已发布文件与准备中的产物分开。若只知道“运行中”，就显示这一粒度，不编造“分析 80%”。断流后将现场标为观察暂不可用，保留最后确认时间，回查 snapshot。

完成后，现场收束成“做了什么、用了哪些版本、产生什么”的可查记录。再次使用成果时选择已发布文件长期保存/授权，或引用 completed Artifact 作 input/evidence。所谓回放只是查看保留事件，不承诺恢复所有历史流式正文，更不是重新执行。

### 视觉、动效与空间

视觉类似简洁的舞台调度图：稳定的对象锚点、少量有方向的连接、短暂事件高亮。活动轨迹只在有真实事件时推进；等待用明确原因和静止状态表示。不同尺度分别看“这项工作”“这次运行”“一个事件”，而不是默认铺开庞大节点图。文本列表提供同等信息，支持减少动效。

### 完整交互故事

1. 陈女士委托研究家庭空气净化器，明确来源范围、预算和需要核对的成果。
2. 工作被接受，舞台出现对应 Run；如后端给出可见分支，才显示分支及真实状态。
3. 她看到某份已授权清单被固定到具体版本；候选中的其他文件仍标“未确认读取”。
4. 如果发生文件操作审批，现场把操作对象、影响和有效期展开；批准后等待执行事实，不能立刻把目标物标为完成。
5. 网络断开，活动动画停止并提示观察中断。重新连接后权威状态显示执行已经结束，现场直接更新到真实终态。
6. 她打开报告、检查证据和保存状态，完成适用的验收；后续从报告返回现场查看来源，而不翻找聊天历史。

### 亮点、风险与可行性

| 项目 | 判断 |
| --- | --- |
| 独特价值 | 把过程透明度变成产品体验，复杂执行的“等在哪里”可被直接理解 |
| 使用风险 | 容易变成开发者控制台或假忙碌可视化；用户可能误读节点为可编辑计划、动画为真实思考 |
| 基础可行性 | **[现]** C05/C08、W03/W05/W13、F07、H04；**[前]** 事件到用户动作语言的映射、分层观察、真实关系图；不依赖统一 SSE |
| 愿景扩展 | **[扩]** 可持久编辑的执行 DAG、可靠工时预测、任意团队调度、完整历史回放存储；需要新控制和事件契约 |
| 待核与恢复 | G06/G07/G11；过程粒度以实际数据为限；chat 流缺口与 Work 持久事件恢复分别处理；普通用户默认只看摘要 |
| 适用边界 | 最适合复杂、长时、需信任建立的工作；简短问答或单次提醒不必展开舞台 |

## 6. 方向 D：成果生长台——先看到想得到的东西，再与 AI 合作完成

### 核心创意与第一幕

设计哲学：用户常常想要一份报告、一张比较表、一个可用的 HTML 页面，而不是想要一段聊天。让成果从明确意图开始逐步形成，交流围绕成果发生。

第一幕呈现最近的成果及其真实状态，也提供“我想得到……”入口。首次使用时用户选择成果类型并写要求，出现带有清晰“目标示意、尚未生成”标记的轮廓；绝不将前端占位内容伪装成 AI 已产生的草稿。

```text
想得到的成果 → 要求与材料 → 生产中的版本 → 已完成版本
                                             │
                         来源 / 保存 / 原交付 / 再加工
修改意图 ───────────────────────────────────→ 新版本
```

### 对象组织与发起方式

成果是入口，Work 是生产委托，Conversation 是来源和修改讨论，长期资源是原料及归档位置。Artifact Version 和 Workspace revision 在用户语言中都可称“版本”，但详情必须分别解释，不合成同一条历史。

研究成果可由研究 Work 生产 **[现]/W03/H04**。从普通表达生成 HTML，基础路径先完成一次助手回答，再由该 completed 非空消息发起独立 Artifact 构建 **[现]/H01**；体验可连续，但必须呈现两个已接受的执行及各自状态，不能假造“任意空白画布直接创建 Artifact”的接口。

### 执行变化与成果复用

工作时保留稳定的目标和最近成功版本，旁边出现构建中的新版本。数据不足时只显示生产状态，不在 HTML 中插入假局部成果。预览失败只影响观看，不改变生产结果。

修改可从用户选中的要求段落或产品外层标注发起 **[前]**：把所选文字和修改要求整理为 instruction，提交前可核对。基础方案不承诺读取任意 sandbox iframe 的 DOM、直接拖改里面的控件、局部像素级准确修改，或严格基于任意旧版分叉。

查看、下载、长期源码副本保存、用于新 Work、原交付验收分别可选。严格“按我当前所见版修改”需解决 G03 的后端 parent CAS **[扩]**；基础版复核最新成功版本并提示并发局限，不承诺消除竞态。研究 Artifact 手改能力列为 **[待核]/G04**。

### 视觉、动效与空间

成果拥有最大视觉权重，生产过程以薄的状态层包围。新版本完成后以可控的揭示或并置比较出现，不自动替换用户正在看的旧版。文本可做本地差异比较；HTML 并排预览不宣称自动理解语义差异。视觉像作品修订桌，但不局限于美术创作；版本、来源和交付事实始终能找回。

### 完整交互故事

1. 郑先生选择“可交互 HTML 清单”，写明用于家庭搬家，并提供获准使用的文字材料。
2. 助手完成内容建议后，他确认“生成 HTML”，独立构建工作才被创建；界面保留内容来源。
3. 构建期间只显示版本排队/运行状态。v1 完成后，他在 sandbox 中试用清单。
4. 他提出“按房间分组，并增加打印说明”。界面核对最新成功版本，提交修改；v1 仍可查看，新版单独构建。
5. v2 预览加载失败时，他重新加载预览，不能把整个构建重新提交。成功后比较 v1/v2，选择下载 v2。
6. 他将源码作为 `.html.txt` 长期保存，明确这不是公开网站，也不是自动授权。
7. 下次从成果发起新的整理 Work，选择具体 completed Artifact 作为 input/evidence；旧成果的原始交付身份保持不变。

### 亮点、风险与可行性

| 项目 | 判断 |
| --- | --- |
| 独特价值 | 用户围绕可使用的结果协作，产物不再埋在对话底部 |
| 使用风险 | 容易被理解成通用文档编辑器或任意格式生成器；漂亮预览掩盖来源、保存和验收差别 |
| 基础可行性 | **[现]** H01–H04、W03/W11、F04/F05；**[前]** 连续两段生产体验、本地版本比较、外层修改锚点、成果索引；账户级全量成果需按已有来源发现，不能假设有全局 Artifact 列表接口 |
| 愿景扩展 | **[扩]** 严格指定 parent、任意版本分叉/合并、持久标注、结构化可编辑成果 schema、公共发布；这些改变成果生产/存储契约 |
| 待核与恢复 | G03/G04/G08；修改冲突保留草稿；生成失败、读取失败、预览失败、提交未知各自恢复 |
| 适用边界 | 最适合研究、报告及 HTML 成果；提醒和没有可视产物的委托应退回简洁表达 |

## 7. 方向 E：时间管家——把持续工作组织成生活节律

### 核心创意与第一幕

设计哲学：持续 Agent 的价值在于人离开之后仍按约定工作。时间应表达“何时启动、何时应再关注、哪一轮已有结果”，而不仅是消息发送时间。

第一幕是“今天与下一次”：已有成果、需要决定的阻塞、即将触发的委托，以及后续持续节律。没有时间的即时工作也有明确入口，不能为了排进日历而伪造完成期限。

```text
过去：实际运行与成果  │  现在：需要关注  │  未来：已确认的触发计划
      研究第 N 轮     │  待验收 / 阻塞  │  明日 09:00 启动下一轮
                    同一持续 Work 贯穿多轮
```

### 对象组织与发起方式

Work 是持续承诺，Run/成果是每轮足迹，Conversation 是安排与临时讨论，长期资源是下一次执行可使用的材料。过去显示实际事件；未来显示计划预测并标明依据，二者不能使用相同“已落实”样式。

用户通过“现在做”“指定时刻开始”“每天做”发起。可拖动时间点预填一次/每日计划，但需核对时区、计划类型和修订影响。一次任务的 due_at 是触发语义，不能承诺在该时刻产出最终结果。基础版仅支持 immediate/once/daily；每周、任意 cron、外部日历同步和智能空档安排为 **[扩]**。

### 执行变化与成果复用

计划到时并不直接变成运行中，要等真实 Run。每日完成一轮后，今日足迹保存，持续 Work 仍可 active；暂停必须显式恢复。错过一次计划按 catch_up，daily 按 latest 合并积压，不画出系统不会实际补跑的全部历史任务。

成果按轮次和时间检索，可以并置比较已有报告/版本，但历史明细存在接口范围上限，必须说明加载覆盖。将上一轮成果用于另一项工作需显式引用或授权；不暗示系统自动学习所有历史成果。

### 视觉、动效与空间

采用可折叠的时间带和清晰的节拍标记，近期展开、远期压缩。状态改变时，计划标记与实际事件建立联系，不做“时间到了成果自动落下”的动画。显示绝对日期、当地时间与必要时区；不靠颜色区别计划、运行和完成。移动端使用顺序日程，避免精细拖拽成为唯一操作。

### 完整交互故事

1. 许女士设定“每天 09:00 研究我关注领域的公开资讯”，确认 Asia/Shanghai、ongoing、来源策略、累计预算与已有合法通知目标。
2. 时间带显示“每日 09:00 触发”，不写“09:00 报告必定送达”。首次 Run 按真实调度进入现场。
3. 当天成果生成并满足保存要求后，时间带出现这一轮报告；渠道接受和验收分别显示。
4. 第三天预算不足，后续承诺仍在，但时间带明确标出阻塞，不能继续展示为每天均会正常产出。
5. 她增额并核对继续条件，或选择暂停。暂停生效后未来标记变为“已暂停”，没有暗中自动恢复。
6. 出差归来显式恢复，界面按后端最新继续条件呈现；不承诺补出所有暂停期间的报告。
7. 她比较两份已存在的报告，保存需要保留的成果，并将其中具体版本引用到一次专题研究。

### 亮点、风险与可行性

| 项目 | 判断 |
| --- | --- |
| 独特价值 | 把“离开产品仍在被照料”的体验变得可理解，清楚表现持续委托和每轮结果 |
| 使用风险 | 容易退化成日历；用户可能误把启动时间当交付期限，或把预测出现次数当承诺执行次数 |
| 基础可行性 | **[现]** W04–W07、W10–W12、H04；**[前]** 时间带、轮次聚合、时区表达、已确认计划的有限预览；扫描不完整不报全历史总数 |
| 愿景扩展 | **[扩]** weekly/cron、外部日历、基于事件触发、可靠完成时间预测、自动排程与冲突协调 |
| 待核与恢复 | G11；真实调度/长期恢复需验收；未知投递不自动再发；跨 DST 时显示既有 first fold/跳过规则 |
| 适用边界 | 最适合提醒、每日研究和周期照料；开放式创作或一次性深度问题不以时间为主入口 |

## 8. 方向 F：资料关系桌——拿着材料直接工作，沿来源找回结果

### 核心创意与第一幕

设计哲学：用户不应先猜文件、对话和成果在哪个模块。资料既是工作的起点，也是连接过去执行与未来用途的稳定锚点。

第一幕是近期使用的资料与产物，围绕当前选中对象只展示一层已知关系：“来自哪次运行”“哪些已查询的委托获准使用”“有哪些版本或衍生产物”。不是自动声称已索引全账户的语义知识图谱。

```text
原始资料 ── 授权给 ──→ 委托
   │                      │
   └─ 固定版本 / 实际读取 ─→ 本轮运行 ── 产生 ──→ 成果
                                                  │
                                          长期入口 / 新用途
关系必须有类型、对象和可核对依据；相邻不等于授权
```

### 对象组织与发起方式

长期 entry 是稳定入口，File 是不可变字节，revision 是内容沿革；任务、对话和成果沿已知关系出现。相同文件在多个位置出现时以同一身份表达，避免看起来保存了多份。

用户选择两份资料，点“让管家处理这些”，写目标或选择研究/比较等意图预设。预设只是请求方式，不承诺所有文件分析工具已开放。拖线或拖入目标只预填授权草稿，随后明确核对主体、操作和递归；提交后等待确认。用于新 Work 的已发布 output，可通过长期 entry grant 再用，不强塞入仅接受 purpose=input 的 input ref。

### 执行变化与成果复用

授权连线、候选连线、实际读取连线分别表达事实，不能用一条“已使用”线概括。撤权后连线变为历史关系并展示当前有效授权；若有其他 grant 仍生效，不能宣称资料完全不可访问。新成果以新对象出现，与原 Run 建立血缘。

用户可从成果逆向回溯到所用版本，再将成果保存、另存或授予下一 Work。更新长期 entry 须走合法 Run 发布输出和版本 CAS；“用新文件替换这个节点”不能绕过该限制。移动/移除 entry 先看真实影响，删除入口不宣称物理字节已清除。

### 视觉、动效与空间

采用可收拢的材料桌，单对象聚焦时才展开关系，连接线上有明确动词。纸张/成品的轮廓用于区分类型，权限不靠颜色暗示。新产物从来源关系旁出现，但仅在发布事实成立后显示。提供等价的关系列表、搜索和面包屑；不要求用户操作无限画布。

### 完整交互故事

1. 罗女士找到两份已保存的家庭设备说明文件，通过文件名、摘要或类型筛选定位；界面不承诺全文语义搜索。
2. 她选中资料，发起维护建议研究，确认新 Work 的读取权限及必要输出安排。
3. 运行出现后，关系桌显示冻结候选和后续实际使用证据；没有使用证据的文件仍只是可用候选。
4. 她撤回一份资料的某条授权。系统核对有效规则与受影响运行，界面分别显示撤权和执行收敛，不假称已忘记读过的内容。
5. 运行若因此阻塞，依据真实继续条件修订或恢复；不能用普通重试绕过权限。
6. 获得合法产出后，她另存到长期空间。若尝试更新既有 entry 遇到版本冲突，保留输出并允许另存，不覆盖别人已提交的版本。
7. 数月后，她从该报告的来源关系找到原资料版本，再显式授权新 Work 做进一步整理。

### 亮点、风险与可行性

| 项目 | 判断 |
| --- | --- |
| 独特价值 | 把资源授权和结果溯源变成自然工作动作，长期积累不依赖记住聊天标题 |
| 使用风险 | 关系密集会变成蜘蛛网；连线容易误导因果、授权或全文理解；资料少时价值不明显 |
| 基础可行性 | **[现]** F01–F07、W09/W11、H04；**[前]** 可见对象的一跳关系、权限状态分层、源版本比较和用途草稿；需要分页和渐进查询，不保证反向关系全量齐全 |
| 愿景扩展 | **[扩]** 全账户关系索引、语义检索、自动主题聚类、服务端自定义关系和跨设备布局；自动持续整理需额外策略及授权 |
| 待核与恢复 | G05/G06；旧输入显示历史/不可用；移动参数改变重做影响预览；保存成功授权失败只补后一步 |
| 适用边界 | 最适合资料积累多、重视复用与出处的用户；轻量日常用户默认只看对象列表和一层关系 |

## 9. 第二轮：方案比较

以下是基于 P0 和场景推演的设计判断，尚未经过用户研究。工程风险同时考虑状态真实性、查询组合、交互误解和扩展依赖，不仅是绘图难度。强弱描述用于识别取舍，不加权求总分。

### 9.1 创意、AI Native 与使用效率

| 方向 | 创意与辨识度 | AI Native 特性 | 真实用户使用效率 |
| --- | --- | --- | --- |
| A 责任交接台 | 高：以责任往返代替消息往返；若只剩状态卡片，辨识度会下降 | 高：承认 AI 持续执行、人类仅在必要节点介入 | 多委托、低频查看很高；详细探索需再深入，排序必须可解释 |
| B 事务空间 | 高：沿用户情境穿越对象；必须避免仅把项目文件夹改名 | 高：上下文决定当前工具与工作表面 | 长期事务切换高效；一次问题可能增加组织负担 |
| C 工作剧场 | 很高：真实过程具有独立空间与时间表达 | 很高：运行、资源、分支、阻塞直接驱动界面 | 复杂任务定位问题高效；简单任务易增加注意力消耗 |
| D 成果生长台 | 高：通过目标物及修订形成协作主循环 | 很高：生成和迭代直接围绕可用结果展开 | 报告/HTML 制作高效；提醒、无形委托难统一 |
| E 时间管家 | 中高：时间轴本身常见，持续责任与每轮交付的区别提供辨识度 | 高：突出离开后执行、周期承担与回来接收 | 日常重复工作高效；临时开放问题不应强排时间 |
| F 资料关系桌 | 高：材料的使用权限和成果血缘进入操作主语法 | 高：AI 使用哪些资料、产出什么可以直接核对 | 资料密集工作和复用高效；关系过多时检索反而更慢 |

### 9.2 长期适应性、契合度、风险与扩展性

| 方向 | 复杂任务与长期资源适应性 | 与现有能力契合程度 | 工程实现风险 | 未来可扩展性 |
| --- | --- | --- | --- | --- |
| A | 复杂任务靠深入查看；长期资料需要对象入口补足 | 很高：continuation、审批、预算、验收天然支持交接 | 基础中：跨领域聚合、部分失败和操作资格不能简化错；个性化优先级另有扩展成本 | 高：可接更多委托类型，交接语法稳定 |
| B | 很高：一件事跨多次任务、多种材料，空间长期保留价值明显 | 中高：对象已有，但“持久情境”不是已有服务端实体 | 基础中、完整愿景高：本地组织与持久语义容易混淆 | 很高：可容纳更多生活场景；空间权限和记忆需谨慎设计 |
| C | 复杂过程很强；长期资源管理较弱，需要来源/成果入口 | 高：Run、trace、分支、资源事实可用；不保证细粒度事件齐全 | 中高：异步事实映射、缺口恢复、可访问性和性能复杂；可控 DAG 风险更高 | 高：可接更多执行类型，但不能让日志结构决定整个产品 |
| D | 交付型复杂任务强；长期版本复用强；非成果任务弱 | 高：研究/Artifact/文件已有；直接编辑与严格分叉缺契约 | 中高：双段构建、版本语义、sandbox、安全与 G03 | 很高：未来可增加结构化成果；需要统一引用而非抹平类型差别 |
| E | 周期委托强；资料管理依赖任务关联，复杂临时流程一般 | 高：once/daily、ongoing、投递已有；复杂日程没有 | 基础中：时区、预测/事实区别、轮次覆盖；完整智能排程高 | 高：新触发器和渠道有扩展空间，但每类都需真实调度契约 |
| F | 很高：资料、固定版本、来源和复用都适合作为长期结构 | 高：Workspace/grant/trace 基础扎实；没有全局知识图谱 | 中高：关系完整性、查询扇出、授权误读；语义图谱扩展高 | 很高：可长成个人资料系统；须防止自动索引越权 |

### 9.3 用同一场景检验差异

共同情境：“研究三种家庭采购方案，使用一份已有清单，离开后回来核对报告，再复用成果。”

| 方向 | 用户最自然的起点 | 回来第一眼看到什么 | 最可能付出的代价 |
| --- | --- | --- | --- |
| A | 交代目标，约定何时需要自己决定 | 待决定事项或可接收的原成果 | 想看全程时需要深入 |
| B | 进入“家庭采购”，拿已有情境开始 | 采购情境中最近确认的变化 | 首次要理解如何组织空间 |
| C | 开一场研究，观察它实际做了什么 | 当前执行位置或完成现场 | 过程信息可能超出用户需要 |
| D | 选择“采购比较报告”，描述成品 | 报告、版本及修改入口 | 容易忽略尚未满足的保存/验收 |
| E | 安排何时开始，之后回来接收 | 时间线上的本轮成果和后续安排 | 一次研究未必值得使用时间主轴 |
| F | 选已有清单，对材料发起工作 | 清单旁新增的报告及来源关系 | 初次空账户缺少抓手 |

这六种方案都能完成同一目标，但让用户记住的对象、决定顺序和回访路径不同。P2 应比较这些行为差异，而非只询问“哪个画面更好看”。

### 9.4 互补关系与不能直接混合的部分

| 组合 | 为什么互补 | 可以融合什么 | 必须避免什么 |
| --- | --- | --- | --- |
| A + E | A 决定现在该关注什么，E 解释将来何时再发生 | 返回时的交接 + 持续承诺的时间表达 | 用未来预测覆盖当前阻塞；强行给所有事情安排时间 |
| A + C | A 降低日常打扰，C 在需要时解释真实过程 | 从交接事项进入对应执行位置 | 首页同时播放所有工作；一切都被包装成紧急待办 |
| B + F | 情境提供人类可记忆的入口，关系提供真实资源结构 | 在情境中展开一层材料来源/使用关系 | 让情境边界变成未经确认的授权边界 |
| B + D | 情境承载长期事务，成果提供明确工作焦点 | 在一个事务中以报告/HTML 成果为阶段中心 | 所有情境都强制产出视觉作品 |
| C + D | C 解释制作过程，D 支持结果审阅和继续加工 | 从生产现场收束到已完成成果，再开新版本 | 过程动画直接变成假成果；把版本生成当原版验收 |
| D + F | D 解决“继续改什么”，F 解决“来自哪里、还能怎么用” | 成果与资料血缘、精确版本复用 | Artifact 版本与长期文件 revision 混为同一版本链 |

不建议同时把 B 的空间、E 的时间轴和 F 的关系图都设为全局主导航。用户应能用一种稳定方式找回工作，其余作为特定目的的视角。A 与 D 的主次也应明确：前者围绕需要人决定的责任，后者围绕成果，两者同时抢占第一幕会造成注意力冲突。

## 10. 第三轮：三个值得深化的融合方向

融合原则：选择一种主语法，再引入解决其弱点的局部交互。统一对象身份、命名、来源和返回路径；不将六个方案各留一个页面拼成新后台。

### 10.1 融合 I：有分寸的管家——责任交接 × 时间节律 × 按需工作现场

**保留的创意：** A 作为整体体验；E 提供持续承诺和每轮结果；C 只在用户想理解过程或处理阻塞时展开。成果用轻量交付包承接，不强制进入创作桌。

**为什么这样组合：** HpAgent 的“云管家”定位需要支持用户离开。A 解决回来后要看什么，E 解释未来仍承担什么，C 提供信任所需的证据。三者共同避免“必须看着 AI 才安心”。

**独特体验：** 用户像交代事情给一个可靠管家：约定目标与边界，离开，回来处理少量确实需要自己的决定。即便没有待办，也能确认哪些委托仍有效、何时触发、最近核对到哪里。

**最有辨识度的核心交互——一次交接，展开一段现场：** 用户点开“预算不足，等待你的决定”，直接看到该 Work 的累计预算、阻塞依据和合法操作；需要了解时继续进入对应 Run，处理后回到同一交接位置。展开的是这次决定需要的事实，不是一整套管理模块。

**一个完整体验片段：** 每日研究已接受 → 用户离开 → 回来看到今日报告与一项阻塞 → 查看报告、验收原版 → 决定是否增额 → 核对后续计划。每一环都保留事实依据；unknown delivery 进入投递核对，不能被“全部处理”批量跳过。

**技术落点：** [现] W04–W12/C05/C08/H04；[前] 责任聚合、时间表达、定向进入执行现场。基础方案不依赖智能优先级或预测完成时间。[扩] 跨设备注意事项状态、个性化优先级、更多触发器是后续独立能力。

**可能的困难：** 用户可能不知道被收起的工作在哪；“交接”语言过于抽象；多次审批打扰。需要始终可达的全部委托、可解释排序和“暂不处理”浏览路径。暂不处理只是本地展示选择，不修改业务期限或解除阻塞。

**适合优先验证：** 普通用户、多项持续委托、低频回访。它是最贴近当前定位的首选候选，但是否足够有辨识度，取决于交接是否真正改变操作链，而非只做一个智能首页。

### 10.2 融合 II：会长出成果的事务空间——情境空间 × 成果生长 × 资料关系

**保留的创意：** B 作为寻找与回访工作的主语法；D 作为成果型任务的聚焦方式；F 提供资料使用和来源的局部展开。提醒等非成果型工作保持简洁，不强套 D。

**为什么这样组合：** 用户处理一件事通常会跨越提问、研究、文件、修改和提醒。B 提供连续情境，D 让工作向可用结果收敛，F 让积累和复用有依据。

**独特体验：** “搬家准备”随着真实工作逐步形成清单、比较报告、提醒和资料关系。产品像一张随事务成长的工作桌；每个新增对象都有来源，每次使用资料都有明确范围。

**最有辨识度的核心交互——带着对象进入下一件工作：** 用户拿起某份报告，选择“基于它继续研究”，界面保留来源锚点并展开新目标和权限草稿。提交后形成新的真实委托和引用，原成果不被覆盖。相同动作可用按钮或键盘完成，不依赖拖拽。

**一个完整体验片段：** 在搬家情境中选资料 → 发起研究 → 聚焦比较报告 → 核对原版成果 → 从报告发起 HTML 清单的合法生产链 → 将清单及提醒保留在同一情境。连续体验跨越多个后端对象，分别显示接受、保存、授权和构建结果。

**技术落点：** [现] W08/W09/W11、F01–F07、H01–H04；[前] 本地情境聚合、按类型呈现、引用草稿、来源展开。[扩] 服务端情境实体和跨设备组织是完整产品体验的重要扩展，不能永远用本地视图冒充；严格版本修改另需 G03 对应契约。

**可能的困难：** 用户可能花太多时间整理空间；空间与目录概念冲突；视图变化造成迷路；“同空间可用”误解权限。需要允许不建空间直接工作，用稳定对象名与返回锚点导航，并在每次发起工作时明确有效资源主体。

**适合优先验证：** 多周事务、资料反复使用、重视成果积累的用户。若用户期待明显区别于聊天机器人的新产品形态，这是最值得大胆深化的候选；代价是必须认真决定情境的持久语义。

### 10.3 融合 III：可观察的成果工坊——成果生长 × 工作剧场 × 精确交接

**保留的创意：** D 作为主循环；C 解释生产过程；A 只承担审批、阻塞、预算与验收等责任节点。F 的来源链可作为成果说明，不把关系图升级成全局结构。

**为什么这样组合：** 制作成果时，用户既想看到产物，又需要知道失败、等待和修改发生在哪里。D 提供目标，C 消除黑箱，A 防止用户被全部过程淹没。

**独特体验：** 用户盯住想得到的报告或 HTML，必要时将它展开成生产现场；完成后现场收束回具体版本。界面围绕同一对象的目标、生产、审阅和复用切换，而不是频繁跳去独立模块。

**最有辨识度的核心交互——成果翻面就是它的生产来历：** “翻面”是概念性过渡，可用普通展开实现。正面审阅可用内容，背面查本版本由哪次运行、哪些资源、哪些确认产生。用户明确选版后，后台更新不能偷偷翻到新版。

**一个完整体验片段：** 交代成果目标 → 研究 Work 或完成回答后的 HTML 构建 → 按真实事件查看制作状态 → 阻塞时出现针对性决定 → 新版完成并置审阅 → 分别保存、下载或验收原交付 → 发起下一次加工。

**技术落点：** [现] H01–H04、C05/C08、W03/W11、F07；[前] 成果与执行的连续对象呈现、文本比较、原版交接。[扩] 严格 parent CAS、结构化局部编辑与持久标注是增强，不伪装为当前能力。

**可能的困难：** 容易将 HpAgent 缩窄为创作工具；用户误以为任何成果都可像设计软件一样直接编辑；过程不够细时“翻面”信息有限。需要覆盖纯提醒、无可视产物和普通问答的轻量路径，明确交互粒度由真实能力决定。

**适合优先验证：** 高价值研究、报告生产和 HTML 反复修改。若产品短期最能产生价值的是成果交付，这是最容易被用户直接感知和检验的候选；未必适合作为所有用户唯一主入口。

### 10.4 如何选择，而不提前定案

| 你最希望用户首先感受到什么 | 优先深化 | 必须一起接受的取舍 |
| --- | --- | --- |
| “我可以放心交代，回来只看需要我的事” | 融合 I | 第一幕更克制，创新主要体现在责任流与回访体验 |
| “它真的围绕我的生活事务组织工作” | 融合 II | 情境需要学习；完整持久空间需要后端扩展 |
| “我能看着结果形成，并直接围绕它继续工作” | 融合 III | 成果型任务占优势，需额外照顾非成果任务 |

推荐保持这三个候选到选择阶段。I 更契合广义数字管家，II 的长期组织方式最值得探索，III 的生成与审阅体验最集中。不能仅用一个总分替代对目标用户、使用频率和主要工作类型的判断。

## 11. 所有候选共享的交互底线与异常故事

这些是概念成立的条件，不是要求固定某种布局或统一做成弹窗。

### 11.1 自适应界面如何可控

| 触发依据 | 可以改变什么 [前] | 保持什么稳定 |
| --- | --- | --- |
| 工作类型：提醒/研究/通用/Artifact 构建 | 时间安排、证据、执行摘要、版本预览的优先级 | 对象名称、当前要求、返回路径、基本控制 |
| 继续条件与 reason | 展开预算、资料、投递或审批对应动作 | 原有上下文、用户草稿、当前选择 |
| 精确成果可用 | 从观察转向可选审阅入口 | 不夺走用户正查看的历史版本，不自动验收 |
| 用户选择深入 | 展开 Run、安全诊断或一层资料关系 | 明确当前主体与所选版本 |
| 观察通道断开 | 显示最近核对时间、恢复读取入口 | 不推断业务已停止或失败 |

基础版是**事实驱动的有限界面变化**。若未来要让模型任意生成整个业务操作界面，属于 [扩]：需要可验证的操作 schema、权限约束、无障碍规则和执行确认边界。生成 HTML 成果只能运行在受限预览里，不能直接承接账户级高风险控制。

### 11.2 同一套责任语言，保留不同恢复方式

| 用户遇到的事 | 合理的界面表达与下一步 | 禁止的捷径 |
| --- | --- | --- |
| 创建委托时断网 | “尚未确认是否接受”；保留同一意图，回查/按原 key、body、version 恢复 | 新建另一项相同委托 |
| 保存完成，但授权失败 | “资料已保存，这项委托暂未获准使用”；只补授权 | 重传、重存，或显示整体成功 |
| 执行中补资料 | 明确已保存/已授权与何轮可用；回读 continuation，必要时走合法修订/领域恢复 | “已补齐，自动继续”，尤其 G10 未解决时 |
| 暂停/停止后仍有未知责任 | 显示正在暂停/停止及未决原因；等待收敛 | 动画停了就显示已停止 |
| 运行失败 | chat 仅安全 failed 可 retry；Work 根据继续条件恢复/推进 | 对 cancelled 做 retry，或用 chat retry 恢复 Work |
| 投递不确定 | 核对渠道接受、未发送或明确承担重复风险的重试；资格由当前事实决定 | 自动重复投递，或把渠道接受记成已读 |
| 另一个客户端修改了要求/版本 | 保留草稿，展示当前基准并重新核对；文件更新冲突可另存输出 | 覆盖新要求、假装 Artifact 已有严格 parent CAS |
| HTML 无法预览 | 重新加载预览或读取/下载原内容，保留版本生产状态 | 重新生成，或将已完成版本改成失败 |
| 会话失效/切账户 | 清理敏感草稿、模型观察和缓存；重新验证身份 | 将前一账户内容作为当前管家的上下文 |

### 11.3 让创新交互在真实设备上可用

空间、拖线、时间拖拽、翻面和缩放都只是可选表达；同一操作必须能通过文字入口和键盘完成。减少动效模式保留全部状态。颜色、动效和位置都不能独自承担状态含义。窄屏优先保留对象、当前责任和下一步，关系与过程按需展开。

每个方向都保留普通问答入口，避免小问题被迫变成正式委托。输入“提醒我……”与“解释一下……”可以走不同业务路径，但任何自动路由都应让用户理解最终创建了 Conversation/Run 还是持续 Work。未实现可靠结构化解析时，不以自然语言动效遮盖不确定性。

## 12. 后端扩展机会：保留想象力，同时说明新增的责任

下面不是本轮实施清单，也不是进入 P2 的前提；它用于判断哪些创意值得投资。

| 扩展 | 支持的愿景 | 需要新增或明确的契约 | 无扩展时的诚实基础体验 |
| --- | --- | --- | --- |
| 持久情境与偏好 | B / 融合 II 的跨设备生活事务 | 情境实体、对象引用、版本/删除语义、账户隔离；偏好与资源授权分离 | 本地聚合视图 + 真实对象检索 |
| 受约束的意图预演 | A/B/E 的“交代后先看方案” | 只读/不执行的解析结果、可编辑草稿 schema、确认后幂等提交 | 用户填写可核对委托；或现有 Main 工具路径，清楚说明已产生的事实 |
| 补资料后的显式恢复 | 多方向中自然的“交回管家” | 明确满足哪项输入条件、哪个 revision 可继续，以及幂等/冲突规则 | 保存、授权分开确认，回读条件，不承诺自动恢复 |

| 资料关系与语义索引 | F 的全局知识组织 | 索引范围、反向引用、撤权传播、搜索权限、完整性和更新语义 | 名称/摘要/类型过滤，可见对象的一跳真实关系 |

不建议把“自由组建 Agent 团队”当作产品辨识度的必要条件。现有有界分支足以支持真实过程观察；普通用户更关心工作是否被负责完成。若未来引入团队、共享或公开发布，应作为新的产品能力讨论，不借视觉隐喻提前承诺。

## 13. 等待选择：P2 可以验证什么

本轮到此停在创意选择，不生成高保真图片、组件或最终布局。下面只约定选择后的验证问题，不在本轮执行。

建议用以下四类任务检验选中方向：临时提问、使用长期资料的一次研究、每日持续委托、成果修改与复用。再加入断流、部分保存成功、版本冲突和未知投递四类扰动，观察用户是否仍理解发生了什么。

| 验证问题 | 要观察的证据 |
| --- | --- |
| 能否不依赖翻聊天找到成果？ | 用户通过委托、情境或成果路径找到正确版本，并说明来源 |
| 能否理解持续 Work 与单次 Run？ | 用户知道停止什么、每日完成一轮后谁仍承担责任 |
| 能否理解资料如何被使用？ | 用户能区分已保存、已授权、候选与实际读取，并指出授权主体 |
| 动态变化是否帮助工作？ | 用户能预测返回路径，界面不夺焦点，不把等待当失败 |
| 是否有真正的管家感？ | 用户敢离开并回来接收，能解释当前等谁、下一步该做什么 |
| 融合是否过度？ | 完成一次主场景不必学习三种并列全局导航 |

可选择一个融合方向，也可以选择一个原始方向作为主语法，再指定借用的局部交互。尚待决定的是产品体验重心，不是布局细节。收到选择后再进入 P2。
