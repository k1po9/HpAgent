## 2. 原则：先显式填写原生参数，再增加校验

本阶段沿用 `extra_body` 表达供应商原生请求字段：运行配置是具体值的唯一来源。以后新增能力描述时只记录哪些字段和组合合法，不再存第二份运行值，更不在发请求时偷偷改写字段。

统一语义的“思考开关/强度”转换是更后面的能力。先不要把 `enabled`、`adaptive`、`high` 或token预算强行映射为同一种概念。

| 控制 | 含义 | 处理原则 |
| --- | --- | --- |
| 思考开关 | 是否启用该模型的思考模式 | 只使用具体模型支持的原生开关 |
| 推理强度 | 请求模型使用某种推理档位 | 不同模型枚举和语义可能不同，不自动把medium改成high |
| 思考预算 | 思考过程允许的token预算 | 不与输出max_tokens或强度档位混为一谈 |
| 未指定 | 使用供应商/模型默认行为 | 与显式false不同，不能自动当作关闭 |

SiliconFlow当前Chat Completions文档列出 `enable_thinking`、`thinking_budget`；`reasoning_effort`只列举了指定模型及其取值。通用接口文档不能替代每个模型的能力证明，也不能因为兼容OpenAI消息格式就认定所有扩展字段一致。

依据：[SiliconFlow Chat Completions](https://docs.siliconflow.cn/docs/api/chat-completions-post)、[推理模型说明](https://docs.siliconflow.cn/docs/userguide/capabilities/reasoning)。实施时重新核对对应模型的当前文档与实际服务，保存核对日期。

## 3. 三条链逐项处理

模型ID来自当前私有配置的脱敏检查，不包含API Key；之后以实际解析出的ID为准。

| 链 | 当前选择 | 旧参数 | 期望行为与候选 | 实施条件 |
| --- | --- | --- | --- | --- |
| fast | zai-org/GLM-5.3-Flash | thinking.type=disabled | 优先低延迟摘要；候选enable_thinking=false | 先确认此具体ID可用且允许关闭思考；当前公开检索不足以证实该ID的参数能力 |
| chat | deepseek-ai/DeepSeek-V4-Flash | thinking.type=disabled | 保持原关闭思考意图；候选enable_thinking=false | 核实该模型对开关、工具调用及输出的支持，再真实探测 |
| reasoning | zai-org/GLM-5.3 | 原thinking.type=adaptive已删除 | 维护者现已明确填写enable_thinking=false，保持关闭意图 | 不是将adaptive自动转换为false；仍需验证此ID支持关闭，不能凭其他GLM版本推定 |

每条链的处理步骤：

1. 确认完整模型ID与账号权限，包括Pro前缀及大小写。模型目录只证明可选ID，不证明全部参数能力。
2. 查对应接口/模型文档，记录开关、枚举、预算范围、默认值、工具调用约束及依据。无法确认的标记“未知”，不当作支持或不支持。
3. 在源码 `config/models.yaml` 删除该链旧的 `thinking` 块，填经确认的原生参数。不要同时保留两种开关，避免互相冲突。
4. 先不加非必需的 `reasoning_effort` 或 `thinking_budget`；只有明确需要且有支持依据时再添加。减少首次验证变量。
5. 未证实某模型允许关闭时，不悄悄删除参数并宣称“关闭成功”；应选择经确认的可用模型，或明确接受供应商默认行为后再配置。
6. 文档更新实际选择与验证状态；本机渲染检查、离线请求体检查通过后，再执行真实验证。

通过具体模型支持核实后，链条可以整理成下面的简洁形式（示例，尚未应用；不要直接整段覆盖其他链参数）：

```yaml
chat:
  - provider: siliconflow
    model: "${SILICONFLOW_STANDARD_MODEL}"
    max_tokens: 4096
    timeout: 30.0
    # 原生参数：该具体模型支持情况及核对日期记录在验证报告中。
    extra_body:
      enable_thinking: false
```

`extra_body`是本项目配置层的容器，线上JSON直接出现 `enable_thinking`，不是再套一层 `extra_body`。

Hindsight不复用这套Worker参数合并流程。它使用自己的模型客户端/适配器；其MiniMax兼容性、结构化输出、记忆提取与召回要另验，不通过更改chat参数顺带“修复”。

## 4. 真实验证方案

本轮只制定步骤；没有开始以下调用。实施时每个样本都可能产生供应商用量，不启动整套业务来替代小范围探测。

### 先离线，再真实

1. 用假的凭据和固定消息调用 `ModelClient.prepare_request()`，不发送HTTP。检查最终JSON字段名、值的类型、工具格式和旧参数是否完全移除。
2. 用HTTP模拟响应验证：参数错误能清楚分类；认证、配额、模型不存在、超时不会被误判为“不支持思考”。
3. 对每条启用文本链做一个小型真实正常请求，使用同一生产序列化流程，不以手写curl成功代替项目请求成功。第一条失败先分类定位，避免批量重试放大费用。
4. 再测试fast的短摘要，以及chat的一个工具调用回合、最终回复；Research报告/HTML格式按首发范围补最小样例。
5. reasoning虽然没有业务自动路由，若仍保留为启用端点，也单独验证其实际参数；不改成自动切换来完成测试。
6. 如需验证开关效果，在模型明确支持的前提下做最小对照。仅HTTP200不能证明参数生效；结合提供商可用的响应元数据、usage、reasoning_content等证据判断，不记录完整推理内容。未返回思考字段也不能单独证明已关闭。
7. Hindsight另用受控测试bank/专用账户验证写入、召回和结构化输出，不混入真实用户记忆；记录此前超时是否再现。

### 留什么证据

每条记录：Git SHA/配置指纹、provider、api_format、解析后的model ID、实际参数名和非敏感值、请求时间、供应商请求ID（有则记录）、状态/错误码、耗时、输入输出用量、是否按预期完成业务。

不保存Key、认证头、Cookie、真实用户内容或完整思考文本。原始供应商异常可能包含请求内容，报告必须脱敏。密钥、完整.env、完整Compose展开不进入对话。

文档确认、离线通过、真实请求通过、业务用例通过分别记录，不合并成一个“模型通过”。一次成功也不代表所有参数组合、长期稳定性或所有账户都通过。

## 5. 给后续自适应检查留出的边界

这里的“自适应检查”先定义为识别、校验和指出问题，不等于自动修改用户意图。

### 能力描述和运行值分开

未来可以新增一个能力描述文件（建议 `config/model-request-profiles.yaml`，本轮不创建运行入口），至少绑定：

- provider：服务提供商；同一模型在不同服务商上可能不同。
- api_format：实际协议，不能只按品牌分支。
- 完整model ID或经过验证的明确范围，未知新版本不自动继承。
- 允许的原生字段、类型、枚举、范围和互斥/依赖组合。
- 来源链接、核对日期、文档确认与真实验证状态。

运行值仍只在models.yaml的extra_body中。能力描述不重复写“当前enable_thinking=false”，也不覆盖用户配置。

### 校验应在真正发请求之前

建议接入路径：

```text
配置解析 → 选择准确能力描述 → 合并provider/model原生参数
        → 检查字段、类型和组合 → 构造最终请求
        → 冻结请求/保存快照/预算预留 → HTTP发送
```

必须检查合并后的最终参数，不能只验模型层：provider默认值也可能带来冲突。校验或转换不得发生在请求冻结之后，避免快照、预算与实际发送不一致。

- 已确认不支持的字段/枚举：在发请求前明确报错，指出配置路径及依据，不输出密钥。
- 缺能力描述：标记“未知/未校验”，不伪造“支持”，不自行删除字段继续调用。
- 允许显式使用未经验证配置时，必须在检查结果中明确其状态，不能混成校验通过。
- 静态检查默认不联网。未来需要真实探测时另设显式执行入口，避免“看看配置”变成付费调用。
- 服务端返回4xx不能一律触发自动换字段：模型不存在、权限、额度、网关策略等须分别分类。
- 不自动把low映射high、adaptive映射true；若未来确实支持转换，必须单独声明映射策略和语义损失，并有测试依据。

当前ModelsConfig对链条字段有白名单。不要先往运行YAML加尚未支持的 `request_profile` / `reasoning` 等新字段；未来扩展时同时修改加载器、类型、请求校验、快照和相关测试。仅在实际序列化语义改变时评估serializer版本，不靠改注释冒充新适配器。

## 6. 需要的测试与验收结果

- 每种原生字段：正确值通过，错误类型/枚举/预算范围/冲突组合在HTTP前失败。
- 同一远端模型用于fast/chat时，参数与端点实例仍相互独立。
- 不同provider相同api_format不串用扩展参数；同provider不同模型不盲目继承能力。
- 未知profile显示未知，不猜测；静态检查无HTTP、无费用。
- 参数正确进入冻结的最终请求，后续不可变，预算预留与发送链路顺序不回归。
- 脱敏报告不输出凭据，错误正文也不能间接泄漏。
- 实际模型/业务测试完成后，将对应能力描述状态更新为已实测，并保留明确的测试边界。

## 7. 发布顺序

先把迁回源码的选择及本方案检查、提交；第二阶段再按证据实施原生参数清理和离线/真实测试。通过后从原项目发布已提交版本到Beta，不再手工双向覆盖。同步时保留Beta私有.env、卷与运行目录，不以开发默认值覆盖用户已填密钥或预算。
