本文把 HpAgent Web 的项目定义细化为可设计、可开发、可测试和可验收的 MVP 需求。本文描述产品必须提供的行为和边界，不替代后续详细架构设计、接口定义或数据库设计。

需求优先级使用以下标记：

- **P0**：MVP 上线必需，缺失则核心闭环不成立。
- **P1**：应当在 MVP 中完成；必要时可在不破坏核心闭环的前提下延期。
- **P2**：已识别的后续增强，不属于本次交付承诺。

## 2. 产品目标

HpAgent Web MVP 要为个人用户提供一个稳定、连续、适合长对话的网页入口。用户能够登录、新建对话、连续发送消息、查看 Agent 的流式回复和基础执行状态，并在刷新页面或重新登录后继续历史对话。

MVP 重点验证：

> 用户是否愿意把 Web 作为与 HpAgent 进行正式、持续对话的主要入口，同时继续使用 QQ 进行日常聊天、快速查询和提醒接收。

## 3. 范围

### 3.1 MVP 范围内

- 支持多个相互隔离的个人账号登录与统一身份识别。
- Web Conversation 的创建、列表、查看、重命名和继续对话。
- 文本消息发送、持久化和历史恢复。
- Agent 回复的流式展示。
- Markdown、代码块和基础复制交互。
- 停止生成和失败后重试。
- 聊天区基础自动滚动及用户主动查看历史时的滚动保护。
- Agent 基础执行状态展示。
- 使用统一账号下的长期记忆。
- Web 与 QQ 短期对话上下文默认隔离。
- 多个个人账号之间的数据隔离。
- 桌面浏览器可用，并具备基础响应式布局。

### 3.2 MVP 范围外

- 文件上传、文件解析、文件管理和在线预览。
- 独立任务中心、子任务管理、审批流和复杂任务编排界面。
- 完整工具调用轨迹、内部思维过程或底层运行日志展示。
- 产物中心、版本管理、在线编辑、分享和多人协作。
- 长期记忆的浏览、编辑、删除和精细权限管理界面。
- Web 与 QQ 短期上下文自动合并。
- 聊天模式与模型切换，以及 Prompt、模型、工具或 Agent 人格的自定义配置。
- 重新生成、回复版本关系和版本切换。
- 流式部分回复的精确持久化与恢复。
- 刷新后自动续接原流。
- 跨刷新恢复精确滚动位置等高级滚动能力。
- 语音、视频、多人会话、团队空间和原生移动 App。
- 计费、会员、配额、邀请和组织管理。

## 4. 核心概念与真相源

### 4.1 领域概念

| 概念 | 定义 | 权威归属 |
|---|---|---|
| Account | 一个自然人的统一 HpAgent 身份，可关联 Web 与 QQ 渠道身份 | HpAgent 后端账号服务 |
| Conversation | Web 中一个可独立命名、恢复和继续的短期对话上下文 | HpAgent 后端 Conversation 服务 |
| Message | Conversation 内持久化的用户消息、Agent 消息及必要的系统可见事件 | HpAgent 后端消息存储 |
| Run | Agent 对一次用户请求的执行实例，包含排队、运行、停止、完成或失败状态 | HpAgent 后端执行与编排系统 |
| Session | HpAgent 当前实现中的运行期会话概念，可被 Run 或 Conversation 使用，但不直接等同于 Web Conversation | HpAgent 后端会话与编排系统 |
| Long-term Memory | 跨 Conversation、可按账号召回的稳定事实、偏好、经历和长期目标 | HpAgent 长期记忆服务 |
| UI State | 输入框内容、当前滚动位置、临时加载状态等浏览器交互状态 | Web 前端；不得替代领域数据 |

### 4.2 真相源原则

1. Account、Conversation、Message、Run 和长期记忆必须由 HpAgent 后端创建、验证和持久化。
2. 浏览器刷新或重新登录后，前端必须从后端重新构建 Conversation、消息和执行状态。
3. 前端生成的临时 ID 只用于请求关联或乐观展示；后端确认的稳定 ID 才能成为持久记录标识。
4. 前端不得仅凭组件本地状态宣告消息已保存、Run 已完成或停止操作已成功。
5. 流式传输是后端状态的增量投影，不是唯一存储。断开连接后应能通过后端历史和 Run 状态恢复。
6. assistant-ui 不得成为账号、Conversation、消息历史、长期记忆或 Agent 执行状态的真相源。

## 5. 用户角色

MVP 只有一个业务角色：**个人用户**。这表示所有用户拥有相同的产品角色和权限模型，不表示系统只能存在一个账号。系统必须支持多个个人账号同时使用，并在服务端严格隔离各账号的数据。

该用户：

- 通过 Web 登录并与自己的 HpAgent 交流。
- 只能访问归属于自己 Account 的 Conversation、Message 和 Run。
- 可以在 Web 使用由 Web 与 QQ 共同沉淀的长期记忆。
- 只能访问归属于自己 Account 的数据，不能访问其他个人账号的 Conversation、Message、Run 或长期记忆。

管理员、团队成员、访客和公开分享访问者不在 MVP 角色范围内。

## 6. 核心用户流程

### 6.1 首次进入并开始对话

1. 用户打开 HpAgent Web。
2. 未登录用户进入登录页；已登录用户进入最近一次 Conversation 或空状态页。
3. 用户点击“新建对话”。
4. 系统创建 Conversation，并返回后端生成的 `conversation_id`。
5. 用户输入文本并发送。
6. 系统保存用户消息，创建 Run，并开始流式返回 Agent 回复。
7. Agent 回复完成后，系统保存最终消息和 Run 状态。

### 6.2 返回并继续历史对话

1. 用户重新打开 Web 或刷新页面。
2. 系统恢复登录态并加载 Conversation 列表。
3. 用户选择一个 Conversation。
4. 系统从后端加载已持久化的消息历史和当前 Run 状态。
5. 用户在原短期上下文中继续交流。

### 6.3 停止生成

1. Agent 正在生成或执行时，界面显示“停止”操作。
2. 用户点击停止。
3. 前端向后端发送取消当前 Run 的请求。
4. 后端确认停止结果并返回最终 Run 状态。
5. 前端根据后端确认展示已取消状态。MVP 不要求精确持久化本地已经渲染但后端尚未确认的部分回复。

### 6.4 失败后重试

1. 请求失败时，界面显示可理解的错误和重试入口。
2. 重试请求携带幂等或关联信息，避免重复保存同一条用户消息。
3. 后端决定复用原消息还是创建新 Run，并返回权威结果。

## 7. 功能需求

### 7.1 账号与访问控制

| 编号 | 优先级 | 需求 |
|---|---|---|
| FR-AUTH-001 | P0 | 未登录用户不得访问聊天页面和任何 Conversation 数据。 |
| FR-AUTH-002 | P0 | 登录成功后，后端必须返回或建立可解析到统一 `account_id` 的安全会话。 |
| FR-AUTH-003 | P0 | 所有 Conversation、Message 和 Run 请求都必须在后端校验资源归属，不得信任前端提交的 `account_id`。 |
| FR-AUTH-004 | P0 | 登录态失效时，前端应停止受保护请求、提示重新登录，并避免丢失输入框中尚未发送的文本。 |
| FR-AUTH-005 | P0 | 对需要共享 QQ 长期记忆的用户，Web 身份与 QQ 身份必须预先映射到同一个 Account；MVP 可通过迁移、配置或受控后台流程建立映射。 |
| FR-AUTH-006 | P1 | 用户可在 Web 通过自助绑定页面建立或管理 QQ 身份映射。 |
| FR-AUTH-007 | P0 | 系统必须支持多个个人 Account，并在后端隔离各账号的 Conversation、Message、Run 和长期记忆。 |

### 7.2 Conversation 管理

| 编号 | 优先级 | 需求 |
|---|---|---|
| FR-CONV-001 | P0 | 用户可以新建 Conversation；Conversation 由后端生成唯一 ID。 |
| FR-CONV-002 | P0 | 用户可以查看自己的 Conversation 列表，至少显示标题和最近更新时间。 |
| FR-CONV-003 | P0 | Conversation 列表按最近活动时间倒序排列。 |
| FR-CONV-004 | P0 | 用户可以打开任一 Conversation 并加载其已持久化消息。 |
| FR-CONV-005 | P0 | 不同 Conversation 的短期消息上下文必须隔离。 |
| FR-CONV-006 | P1 | 用户可以重命名 Conversation。 |
| FR-CONV-007 | P1 | 新 Conversation 可根据首条用户消息生成默认标题；生成失败时使用确定性的回退标题。 |
| FR-CONV-008 | P1 | 消息较多时，历史记录应分页或游标加载，且不得打乱消息顺序。 |
| FR-CONV-009 | P2 | 删除、归档、搜索和置顶 Conversation 后续实现。 |

### 7.3 消息输入与发送

| 编号 | 优先级 | 需求 |
|---|---|---|
| FR-MSG-001 | P0 | 用户可以通过多行输入框编辑纯文本消息。 |
| FR-MSG-002 | P0 | 界面应清楚区分“换行”和“发送”，并提供可发现的发送按钮。 |
| FR-MSG-003 | P0 | 空白消息不得发送。 |
| FR-MSG-004 | P0 | 发送后，系统必须由后端持久化用户消息并创建对应 Run。 |
| FR-MSG-005 | P0 | 前端必须为发送请求携带幂等键或客户端请求 ID，避免网络重试造成重复消息。 |
| FR-MSG-006 | P0 | 当后端尚未确认接收时，消息必须显示为待确认状态；失败时允许重试。 |
| FR-MSG-007 | P1 | MVP 应限制单条消息长度，并在前端提示、后端强制校验；具体上限在接口设计中确定。 |
| FR-MSG-008 | P1 | 用户发送消息后清空输入框；发送失败时应能恢复原始文本。 |
| FR-MSG-009 | P0 | 同一账号可在多个浏览器标签页使用 Web；后端必须处理重复请求与并发写入，不能依赖标签页之间自行协调。 |

### 7.4 回复展示与流式交互

| 编号 | 优先级 | 需求 |
|---|---|---|
| FR-STREAM-001 | P0 | Agent 文本应支持增量流式显示，无需等待完整回复结束。 |
| FR-STREAM-002 | P0 | 流式内容完成后，前端展示必须与后端持久化的最终 Message 一致。 |
| FR-STREAM-003 | P0 | 流中断时，前端应展示中断状态，并通过后端查询已保存内容和 Run 状态。 |
| FR-STREAM-004 | P0 | Agent 回复支持 Markdown 渲染，包括段落、列表、引用、链接、表格和行内代码。 |
| FR-STREAM-005 | P0 | 代码块应具备语言标识（后端内容提供时）、横向滚动和复制操作。 |
| FR-STREAM-006 | P0 | Markdown 中的原始 HTML 默认不得以不受控方式执行，链接和代码内容必须安全渲染。 |
| FR-STREAM-007 | P0 | 当用户位于消息底部附近时，新内容自动滚动；用户主动向上查看历史时，不得强制拉回底部。 |
| FR-STREAM-008 | P1 | 用户离开底部后，界面应提供“回到最新消息”的明显入口。 |

### 7.5 Run 控制与执行状态

| 编号 | 优先级 | 需求 |
|---|---|---|
| FR-RUN-001 | P0 | 每次用户请求必须关联一个后端 Run，前端可用稳定 `run_id` 关联流和状态。 |
| FR-RUN-002 | P0 | MVP 至少区分 `queued`、`running`、`completed`、`failed`、`cancelling` 和 `cancelled` 状态。 |
| FR-RUN-003 | P0 | 生成或执行期间显示停止操作；停止必须调用后端取消能力。 |
| FR-RUN-004 | P0 | 后端无法取消、已完成或取消超时时，前端必须展示真实结果，不能只在本地隐藏生成状态。 |
| FR-RUN-005 | P0 | 失败状态应提供面向用户的错误摘要和可行的重试操作，不展示敏感内部堆栈。 |
| FR-RUN-006 | P2 | 用户可以对最近的 Agent 回复发起重新生成，后端创建新的 Run 并管理回复版本关系。 |
| FR-RUN-007 | P0 | 刷新页面后，前端应查询后端并展示当前 Run 状态；MVP 不要求自动续接刷新前的原流。 |
| FR-RUN-008 | P0 | MVP 默认同一 Conversation 同时只允许一个活跃 Run；并发请求必须由后端串行化或以明确冲突响应拒绝。 |
| FR-RUN-009 | P2 | 刷新页面后自动重新订阅仍在运行的原 Run，并继续增量展示原流。 |

### 7.6 后续聊天模式与模型切换

| 编号 | 优先级 | 需求 |
|---|---|---|
| FR-MODE-001 | P2 | MVP 固定使用默认 Agent 行为，不提供“聊天”“任务”等模式选择。 |
| FR-MODE-002 | P2 | MVP 不提供模型切换；后续如开放模式或模型选择，其列表、稳定标识和可用状态必须由后端返回。 |
| FR-MODE-003 | P2 | 模式不得改变 Account、Conversation 和长期记忆的归属。 |

### 7.7 历史恢复

| 编号 | 优先级 | 需求 |
|---|---|---|
| FR-HIST-001 | P0 | 刷新页面后，已确认的用户消息和 Agent 消息不得丢失。 |
| FR-HIST-002 | P0 | 重新登录后，用户可以重新获取自己的 Conversation 列表和消息历史。 |
| FR-HIST-003 | P0 | 历史消息顺序由后端序号或游标决定，不依赖浏览器接收时间。 |
| FR-HIST-004 | P0 | 前端检测到流事件缺失、重复或乱序时，应以重新获取的后端状态为准。 |
| FR-HIST-005 | P2 | Conversation 打开时恢复跨刷新保存的精确阅读位置；MVP 仅需默认定位到最新消息并支持基础滚动保护。 |

### 7.8 长期记忆与跨渠道边界

| 编号 | 优先级 | 需求 |
|---|---|---|
| FR-MEM-001 | P0 | Web 请求使用统一 `account_id` 对应的长期记忆空间。 |
| FR-MEM-002 | P0 | 长期记忆召回由 HpAgent 后端完成，前端和 assistant-ui 不持有长期记忆真相。 |
| FR-MEM-003 | P0 | 当 Web 身份与 QQ 身份已映射到同一 Account 时，Web 必须能召回该 Account 通过 QQ 沉淀的长期记忆。 |
| FR-MEM-004 | P0 | Web Conversation 不得自动拼接 QQ 最近消息作为短期上下文。 |
| FR-MEM-005 | P0 | 一个 Web Conversation 不得自动拼接另一个 Web Conversation 的短期消息。 |
| FR-MEM-006 | P1 | 当 Agent 使用长期记忆时，应遵循相关性和隐私边界，避免主动暴露无关渠道细节。 |
| FR-MEM-007 | P2 | 显式跨端继续任务、记忆管理界面和记忆来源解释后续设计。 |

## 8. 前端技术选型：assistant-ui

### 8.1 选型结论

Web 聊天界面优先采用 **assistant-ui** 提供的成熟 React 组件和交互抽象，复用以下通用能力：

- 消息列表与消息角色展示。
- 多行输入框和发送操作。
- Markdown 内容渲染。
- 代码块展示与复制。
- 流式内容增量显示。
- 停止生成入口。
- 基础自动滚动、滚动保护和回到最新消息。
- 加载、空状态和基础错误状态的交互骨架。

assistant-ui 已具备但本次 MVP 不启用的重新生成等交互，可在对应后端能力完成后作为 P2 接入。

优先采用不代表无条件锁定。实现前应通过最小集成验证确认其版本、许可证、可访问性、主题定制能力、流协议适配成本和 React 技术栈兼容性；若关键 P0 需求无法满足，应记录决策后替换，而不是扭曲后端领域模型迁就组件。

### 8.2 assistant-ui 的职责边界

| assistant-ui 负责 | assistant-ui 不负责 |
|---|---|
| 聊天界面组件组合 | 用户认证与账号绑定 |
| 消息和流式片段的呈现 | Account 真相与资源权限校验 |
| 输入、发送、停止等交互入口 | Conversation 的创建、持久化和归属 |
| Markdown 与代码块的前端渲染 | Message 历史的权威存储 |
| 自动滚动等浏览器体验 | 长期记忆的写入、召回或管理 |
| 将用户操作传递给 HpAgent 前端适配层 | Agent Run 的创建、取消、恢复和最终状态判定 |
| 展示后端返回的状态 | Temporal、Session、工具执行和模型调用编排 |

### 8.3 集成原则

1. **后端领域模型优先**：先定义 Account、Conversation、Message、Run 的服务契约，再编写 assistant-ui 适配层。
2. **隔离第三方类型**：业务代码不得在全局直接依赖 assistant-ui 的内部消息或运行时类型；在 Web 前端边界集中完成映射。
3. **服务端初始化**：打开 Conversation 时，先从 HpAgent API 获取权威消息，再映射为 assistant-ui 所需的展示结构。
4. **服务端确认**：发送、停止和重试操作都必须调用 HpAgent API，并根据后端确认更新最终状态；后续重新生成也遵循相同原则。
5. **可重连流**：流式适配层应能识别 `conversation_id`、`message_id`、`run_id` 和事件序号；断线后回源后端恢复。
6. **不双写真相**：不得同时把 assistant-ui 本地存储和 HpAgent 后端都当作消息历史数据库。
7. **不泄漏后端细节**：前端组件不直接连接 Temporal、Redis、Hindsight、模型服务或工具运行时。
8. **可替换性**：更换 UI 组件库不应要求迁移 Account、Conversation、Message、Run 或长期记忆数据。

### 8.4 前端建议分层

```text
React 页面与路由
    ↓
HpAgent Chat UI（产品组件、文案、权限与页面状态）
    ↓
assistant-ui（通用聊天交互与渲染）
    ↓
HpAgent assistant-ui Adapter（类型映射、操作转发、流事件映射）
    ↓
HpAgent Web API Client
    ↓
HpAgent 后端（唯一业务真相源）
```

适配层至少负责：

- 后端 Message 到前端消息结构的转换。
- 前端发送操作到后端创建消息/Run 请求的转换。
- 后端流事件到增量展示事件的转换。
- 停止和重试操作的 API 调用，并为后续重新生成预留扩展边界。
- 断线重连、重复事件过滤和最终状态回源。
- 后端错误码到用户可理解界面状态的映射。

## 9. 后端能力需求

本节定义逻辑能力，不锁定最终 URL、HTTP 方法或传输协议。

### 9.1 账号能力

- 获取当前登录用户及统一账号信息。
- 验证每个资源是否归属于当前用户。
- 建立或查询 Web 渠道身份与统一 Account 的映射；P0 不要求提供用户自助绑定页面。

### 9.2 Conversation 能力

- 创建 Conversation。
- 游标分页列出当前用户的 Conversation。
- 获取单个 Conversation。
- 修改 Conversation 标题。
- 返回 Conversation 当前活跃 Run 的摘要。

### 9.3 Message 与 Run 能力

- 游标分页获取 Conversation 消息，提供稳定顺序字段。
- 接收用户消息并以原子或可恢复方式创建 Run。
- 返回后端生成的 `message_id`、`run_id` 和初始状态。
- 传输带序号的流式文本与状态事件。
- 查询 Run 当前状态与已持久化输出。
- 取消 Run。
- 重试失败请求。
- P2 阶段支持重新生成回复和回复版本关系。

### 9.4 建议的流事件最小集合

| 事件 | 用途 |
|---|---|
| `run.started` | Run 已进入执行状态 |
| `message.delta` | Agent 消息的增量文本 |
| `run.status` | Run 状态发生变化 |
| `run.completed` | Run 正常完成，携带已持久化的完整 Agent Message 和 Run snapshot |
| `run.failed` | Run 失败，携带安全错误码与用户可见摘要 |
| `run.cancelled` | 后端确认 Run 已取消 |

每个事件至少应携带可用于关联和去重的 `conversation_id`、`run_id`、事件序号；消息事件还应携带 `message_id`。具体字段由接口设计确定。

### 9.5 传输要求

- MVP 可采用 SSE、WebSocket 或支持流式响应的 HTTP 方案，最终选择由技术设计决定。
- 选择必须支持身份校验、取消、断线检测、事件排序和状态回源。
- 客户端断开不等于后端 Run 自动取消；是否继续执行由后端策略决定。
- 任何流协议都不得成为消息持久化的唯一机制。

## 10. 页面与界面状态

### 10.1 MVP 页面

| 页面/区域 | 必需内容 |
|---|---|
| 登录页 | 登录入口、失败提示、返回聊天页逻辑 |
| 聊天工作台 | Conversation 列表、新建对话、当前对话标题、消息区、输入区 |
| 空状态 | 产品定位简述、新建或开始对话入口 |
| 全局错误状态 | 网络异常、登录失效和服务不可用提示 |

### 10.2 聊天区状态

聊天区至少覆盖：

- Conversation 初次加载。
- Conversation 无消息。
- 历史消息加载成功或失败。
- 用户消息等待后端确认。
- Run 排队、运行、取消中、已取消、完成和失败。
- 流暂时中断，以及通过查询后端恢复已持久化消息和 Run 状态；MVP 不保证继续原增量流。
- Conversation 不存在或无权限。

## 11. 非功能需求

### 11.1 安全与隐私

| 编号 | 优先级 | 需求 |
|---|---|---|
| NFR-SEC-001 | P0 | 所有受保护接口必须鉴权并进行服务端资源归属校验。 |
| NFR-SEC-002 | P0 | Markdown 和代码块渲染必须防止 XSS；用户内容不得执行任意脚本。 |
| NFR-SEC-003 | P0 | 日志、错误消息和流事件不得包含令牌、密钥或内部敏感堆栈。 |
| NFR-SEC-004 | P0 | 传输层在生产环境必须使用 TLS。 |
| NFR-SEC-005 | P1 | 登录凭据优先使用安全、HttpOnly、SameSite 合理配置的 Cookie 或同等级方案，避免持久化到可被脚本直接读取的位置。 |

### 11.2 可靠性与一致性

| 编号 | 优先级 | 需求 |
|---|---|---|
| NFR-REL-001 | P0 | 已被后端确认的消息在页面刷新后可恢复。 |
| NFR-REL-002 | P0 | 重复提交或流事件重放不得产生重复持久消息。 |
| NFR-REL-003 | P0 | 最终界面状态必须能够通过后端 API 校正。 |
| NFR-REL-004 | P1 | 服务重启后，已持久化 Conversation 和 Message 可恢复；进行中的 Run 显示可解释的最终或恢复状态。 |

### 11.3 性能体验

具体数值应在基线环境确定后固化，MVP 暂定目标如下。指标测试基线必须在系统设计阶段明确，至少记录本地或测试环境配置、历史消息数量与长度、网络条件，以及计时的起止点；未声明测试基线的测量结果不用于判定是否达标。

| 编号 | 优先级 | 目标 |
|---|---|---|
| NFR-PERF-001 | P1 | 正常网络下，打开已有 Conversation 后 2 秒内展示首屏历史消息。 |
| NFR-PERF-002 | P1 | 后端开始输出后，流式文本在前端的可见延迟不高于 500 毫秒。 |
| NFR-PERF-003 | P1 | 长 Conversation 采用分页或虚拟化策略，消息数量增长时不应导致页面明显失去响应。 |

### 11.4 兼容性与可访问性

| 编号 | 优先级 | 需求 |
|---|---|---|
| NFR-UX-001 | P0 | 支持当前主流桌面版 Chromium 浏览器。 |
| NFR-UX-002 | P1 | 基础布局在常见手机宽度下可完成查看、输入和发送，但不承诺原生 App 体验。 |
| NFR-UX-003 | P1 | 核心操作可通过键盘完成，交互控件具备可理解的标签和焦点状态。 |
| NFR-UX-004 | P1 | 流式更新和状态变化不应造成不可控焦点跳转。 |

### 11.5 可观测性

| 编号 | 优先级 | 需求 |
|---|---|---|
| NFR-OBS-001 | P0 | 后端日志可通过请求 ID、`conversation_id` 和 `run_id` 关联一次请求链路。 |
| NFR-OBS-002 | P0 | 记录发送失败、流中断、Run 失败和取消失败等关键错误指标。 |
| NFR-OBS-003 | P1 | 记录核心漏斗事件，但不得把完整私密消息正文发送到产品分析系统。 |

## 12. MVP 验收场景

### AC-001：完整长对话闭环

给定用户已登录，当用户新建 Conversation、连续完成至少三轮对话、刷新页面并重新打开该 Conversation 时：

- 所有后端已确认消息按原顺序展示。
- 用户能够继续发送消息。
- 新请求只使用当前 Conversation 的短期上下文。

### AC-002：Conversation 隔离

给定同一用户存在 Conversation A 和 B，当用户在 B 中提问时：

- 后端不会自动把 A 的短期消息加入 B 的上下文。
- B 仍可按统一 Account 使用相关长期记忆。

### AC-003：流式回复与刷新恢复

给定 Agent 正在流式回复，当连接中断或用户刷新页面时：

- 页面不会把本地缓存内容直接认定为最终消息。
- 页面从后端恢复已持久化消息和 Run 状态。
- 不产生重复的用户消息或 Agent 消息。

### AC-004：停止生成

给定 Run 正在执行，当用户点击停止时：

- 前端向后端提交取消请求。
- 只有收到后端确认后才展示 `cancelled`。
- 前端不把本地已渲染片段当作已持久化结果；MVP 不要求精确恢复未被后端确认的部分回复。

### AC-005：失败后重试

给定一次消息发送或 Run 执行失败，当用户点击重试时：

- 后端根据幂等键或原请求关联信息处理重试。
- 不会重复保存同一条用户消息。
- 前端展示后端确认的新 Run 状态和最终结果。

### AC-006：assistant-ui 非真相源

给定清空浏览器临时状态或更换浏览器，当用户登录并打开同一 Conversation 时：

- Conversation、Message 和 Run 状态可从 HpAgent 后端恢复。
- 长期记忆仍由后端按统一 Account 使用。
- 产品正确性不依赖 assistant-ui 的本地缓存。

### AC-007：越权保护

给定系统中存在多个个人账号，且用户尝试访问不属于自己的 `conversation_id`、`message_id`、`run_id` 或长期记忆：

- 后端拒绝请求。
- 响应不泄露该资源是否存在、消息正文或其他账号信息。

### AC-008：安全渲染

给定消息包含脚本、危险 HTML 或恶意链接内容：

- 页面不执行消息中的脚本。
- Markdown 与代码仍能以安全方式阅读和复制。

### AC-009：QQ 长期记忆共享

给定某个用户的 Web 身份和 QQ 身份已通过 P0 账号映射关联到同一 Account，且该用户已通过 QQ 沉淀一条可召回的长期记忆，当用户在 Web 的新 Conversation 中提出相关问题时：

- 后端使用同一 Account 的长期记忆空间并可召回该记忆。
- Web 不需要用户先完成 P1 自助绑定页面流程；映射可由 MVP 的迁移、配置或受控后台流程预先建立。
- Web 不会把 QQ 最近聊天消息整体拼接为当前 Conversation 的短期上下文。
- 其他个人账号无法召回或访问该记忆。

### AC-010：多标签页并发

给定同一用户同时打开多个浏览器标签页：

- 不同 Conversation 可以独立读取和发送消息，消息不会串入其他 Conversation。
- 两个标签页同时向同一 Conversation 发起请求时，后端保证最多一个活跃 Run，或者对冲突请求返回明确、可重试的冲突响应。
- 请求重放或标签页重复提交不会产生重复持久消息。
- 标签页重新加载后，均以同一份后端 Conversation、Message 和 Run 状态为准。

## 13. MVP 成功指标

第一版上线后重点观察：

- 成功完成首轮 Web 对话的登录用户比例。
- 创建 Conversation 后完成至少三轮对话的比例。
- 七天内返回并继续历史 Conversation 的用户比例。
- 消息发送成功率和重复消息率。
- Run 完成率、失败率、取消成功率。
- 流式连接中断率及中断后的恢复成功率。
- 用户从 QQ 转到 Web 继续正式交流的实际使用情况。

指标定义不得依赖采集完整消息正文，并应在上线前补充统计口径和隐私说明。

## 14. 实现前待决事项

以下事项不阻塞需求评审，但必须在技术设计或开发启动前明确：

1. Web 前端框架、构建工具及 assistant-ui 的具体兼容版本。
2. 登录方式，以及如何通过迁移、配置或受控后台流程完成 P0 Web/QQ Account 映射；用户自助绑定页面属于 P1。
3. Conversation 的持久化模型，以及与现有 Session/Workflow 的映射关系。
4. 流式传输协议、断线后的状态查询策略与事件保留窗口。
5. 后端 Run 取消的真实语义：停止模型输出、停止工具执行或完整取消工作流。
6. 同一 Conversation 并发请求的拒绝或串行化策略，以及冲突错误契约。
7. 单条消息长度、历史分页大小、Conversation 数量和保留期限。
8. 长期记忆召回时的隐私边界及跨渠道来源处理规则。

重新生成与版本关系、部分回复精确持久化、自动续流、高级滚动恢复和模式选择属于 P2，不作为 MVP 启动前置决策。

## 15. 已识别的架构差距

基于当前 HpAgent 实现，MVP 开发前至少需要处理以下差距：

- 当前后端已有 Account、Session、事件流和长期记忆能力，但缺少面向 Web 产品的 Conversation 服务契约。
- 当前“账号对应活跃 Session”的机制不足以直接表达同一用户的多个独立 Web Conversation。
- 需要确保 Web 与 QQ 身份可以在无自助绑定页面的情况下预先映射到同一 Account，并验证多账号数据隔离。
- 需要建立 Message 与 Run 的稳定标识、持久化查询和流事件契约。
- 需要为 Web 增加认证、资源归属校验和浏览器可用的 API 边界。
- 需要把停止、失败重试和并发控制落实为后端能力，而不仅是前端组件动作。

这些差距应在后续技术设计中解决。不得通过把 assistant-ui 的本地运行时状态当作后端 Conversation 或消息存储来绕过。

## 16. MVP 完成定义

当全部 P0 需求和验收场景通过，且不存在会导致消息丢失、Conversation 串话、跨账号越权或执行状态失真的已知严重问题时，HpAgent Web MVP 才可视为完成。

最终核心闭环为：

> 登录 Web → 新建 Conversation → 连续多轮对话 → 查看流式回复和真实执行状态 → 停止或重试请求 → 刷新或重新登录 → 从后端恢复并继续同一 Conversation，同时保证 QQ 长期记忆可共享且多个个人账号、Conversation 和标签页之间不串数据。

## 18. 基线变更管理

本文 0.4 是当前 HpAgent Web MVP 正式需求基线。系统设计可以补充实现细节，但不得在未更新本文的情况下改变以下核心需求：

- 支持多个相互独立的 Conversation。
- HpAgent 后端是 Account、Conversation、Message、Run 和长期记忆的真相源。
- Web 与 QQ 共享账号级长期记忆。
- Web、QQ 及不同 Web Conversation 的短期上下文默认隔离。
- 消息持久化并可在刷新或重新登录后恢复。
- 提供幂等保护和多标签页并发控制。
- 多个个人账号之间的数据严格隔离。
- Run 展示后端真实状态，停止操作由后端确认。

需求发生变化时，必须升级本文版本、记录评审结论并同步更新需求追踪矩阵；不得仅通过代码实现改变产品行为。
